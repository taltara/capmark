# What DSH plugins reach for, and what they say about it

*August 2026. Sixteen published plugins, read with `capmark infer`.*

Nothing here is an accusation. Every package in this sample is doing something
reasonable, and several of them are doing it well — a supply-chain scanner that
reads files is a supply-chain scanner doing its job. The finding is not about
any package. It is that **none of them can tell you what they reach for without
you reading their source**, and that is a gap in the ecosystem rather than a
fault in a plugin.

## The numbers

| | |
|---|---|
| plugins audited | 16 |
| that read the filesystem | **10** |
| that reach the network | 2 |
| that need neither | 6 |
| that declare any of it | **0** |

Reproduce it:

```sh
node scripts/audit.mjs
```

It fetches each package from npm, reads it statically, and prints the same
table. No harness runs, nothing executes.

## What "reach for" means here

Two static signals, both declarations the plugin already makes:

- **Injected services.** A Cordis plugin names the services it needs in a plain
  array at module level — `inject = ['tools']`. Reading it is not inference; it
  is quotation.
- **Node builtins.** `import 'node:fs'` reaches a disk whether or not the
  harness knows about it.

The second one is the reason this audit exists. An earlier version of the
reader followed only the service graph, and it reported those ten
filesystem-reading plugins as capability-free. That answer was worse than no
answer: it looked like a security finding and it was wrong in the reassuring
direction. Six of the sixteen inject `tools` and nothing else, which reads as
"asks for nothing" — while importing `node:fs` on the next line.

One plugin opens raw sockets through `node:net`, `node:dns`, `node:http` and
`node:https`. That is almost certainly deliberate and necessary for what it
does. There is also no way to know that from the package.

## What this does not tell you

Static reading sees what a plugin *can* reach, never what it does. A plugin
importing `node:fs` might read one config file at startup or everything under
`$HOME`, and nothing here distinguishes them. That is exactly why the output is
a **draft manifest for the author to correct** rather than a verdict about the
plugin.

It also cannot see:

- what a plugin does with a dependency's capabilities rather than its own
- anything reached through `eval`, dynamic import, or a native addon
- behaviour that only appears at runtime

A manifest is worth more than this audit precisely because the author knows
those answers and the reader does not.

## The gap, stated plainly

Installing a plugin runs its code in your process with your privileges. The
current answer to "what will this do?" is: read the source, or trust the README.
Sixteen out of sixteen packages here are trustworthy as far as anyone can tell,
and none of them can prove it.

A `CAP.md` is a way to say so in one file that a machine can check:

```
grant fs:read scope=workspace   # reads files under the project
never proc:spawn                # never runs a command
never credentials:read          # never touches the secret store
```

For most of these plugins that file is three or four lines, and most of those
lines are `never`. That is the interesting part: **the ecosystem's problem is
not over-reaching plugins, it is modest plugins with no way to prove they are
modest.**

## If you maintain one of these

`capmark infer <your-package>` drafts the manifest from what your plugin already
declares, with the evidence beside each line. Correcting a draft takes a minute;
writing one from a blank file is why formats like this usually fail.

Happy to open the PR against your repo if that is easier — the draft is
generated, so the work is in the review, and you are better placed to do that
than I am.
